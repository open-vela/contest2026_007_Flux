# Bug 排查与上报流程

## 概述
标准化的bug排查流程，区分业务代码问题和框架/系统问题，分别采取不同的处理方式。

## 触发词
"有个bug" "出问题了" "报错" "崩溃" "异常" "运行不了"等，根据实际内容来判断

## 阶段1：问题定位

### 收集信息
```
1. 收集问题表现（用户描述）
2. 询问关键信息：
   - 复现步骤
   - 错误日志
   - 环境信息
   - 发生频率
3. 定位问题归属：
   - 业务代码？
   - 框架/系统？
```

### 询问清单
- [ ] 具体报错信息是什么？
- [ ] 什么时候开始出现的？
- [ ] 是否必现？概率多少？
- [ ] 有改动过代码吗？
- [ ] 能提供完整日志吗？

---

## 阶段2：分支处理

### 分支A：业务代码问题

```
→ 进入 Plan Mode
→ 分析问题根因
→ 制定修复方案
→ 评估风险点
→ 准备应对方案
→ 执行修复
```

**风险评估要点**
- 影响范围有多大？
- 是否涉及核心功能？
- 修复是否可能引入新问题？
- 是否需要回滚方案？

### 分支B：框架/系统问题

```
→ 询问用户获取更多日志
→ 收集完整信息
→ 生成问题报告
→ 交付用户转交
```

---

## 阶段3：问题报告生成

### 报告模板

```markdown
# 问题报告

## 问题描述
[问题表现]

## 环境信息
- 系统版本：xxx
- 框架版本：xxx
- 设备型号：xxx

## 复现步骤
1. [步骤1]
2. [步骤2]
3. [步骤3]

## 日志信息
```
[完整日志]
```

## 可能的问题源
- [分析1]
- [分析2]

## 建议排查方向
- [方向1]
- [方向2]
```

### 文件命名规范
```
bug-report-[日期]-[简要描述].md
示例：bug-report-2026-08-24-fetch-crash.md
```

### 存放位置
```
项目主文件夹下
```

## 阶段4：交付

### 交付话术

**业务代码问题**
```
经过排查，这是代码层面的问题，原因是[xxx]。
我制定了修复方案，主要风险点是[xxx]，应对方案是[xxx]。
现在开始修复。
```

**框架/系统问题**
```
经过排查，这个问题不在你的代码层面，而是框架/系统的问题。
我已经写了一个问题报告（[文件路径]），你可以把它交给[框架]的开发组，他们会帮助你解决。
```

---

## 最佳实践

1. **先问后查**：先收集足够信息再动手排查
2. **分支明确**：清晰区分业务问题和系统问题
3. **记录完整**：日志、复现步骤、环境信息缺一不可
4. **报告规范**：使用统一模板，方便开发组理解
5. **及时交付**：问题确认后尽快生成报告交付

## 常见问题

### 1. 问题难以复现
- 收集更多环境信息
- 尝试不同复现路径
- 记录偶现问题的规律

### 2. 日志不完整
- 指导用户开启详细日志
- 使用远程调试工具
- 添加临时日志输出

### 3. 问题归属不明确
- 逐步缩小排查范围
- 对比正常和异常情况
- 必要时同时报告给多方
